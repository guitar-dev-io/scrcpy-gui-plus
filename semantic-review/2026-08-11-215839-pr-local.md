# USB AOA Android companion with desktop controls

This change adds a standalone Android companion and a desktop USB AOA transport, separate from ADB and scrcpy. Rust switches a phone into accessory mode, identifies the app through a versioned hello, and serializes allow-listed JSON requests over one bulk connection; React adds scan, clipboard, device-info, URL, and disconnect controls. The Android Activity owns the stream and serves requests only while foregrounded. Message bounds are explicit, but the session lifecycle, cancellation model, and trust boundary still have shipping blockers.

**Watch for:** **likely** `open_url` closes the session it is using; **confirmed** USB work has no end-to-end deadline or cancellation path; **confirmed** backend and React connection state can diverge; **confirmed** clipboard and URL access rely only on accessory permission and self-reported identity; **likely** Windows/Linux need device-access integration beyond vendored `rusb`.

**Verdict**: NEEDS_CHANGES

## High-level view

The sidebar calls three Tauri commands, the backend serializes them through one `CompanionConnection`, and the Android worker processes one request/response at a time. This prevents frame interleaving, but also puts scan, request, and disconnect behind one blocking mutex.

**Likely:** launching a browser from `MainActivity.openUrl` causes the companion Activity's `onStop` policy to close the accessory stream, making an apparently ordinary request terminal and potentially racing its response.

**Confirmed:** five seconds is a per-transfer timeout, not an operation deadline; each rescan performs blocking identification, and disconnect waits for the same mutex. **Confirmed:** when transport I/O fails, Rust can discard its handle while React continues to render the cached device as “Connected.”

**Confirmed:** peer trust consists of Android's accessory permission plus self-reported hello metadata even though the protocol exposes clipboard and URL actions. **Confirmed:** discovery commits to the first AOA-capable device before identifying the companion; **likely:** its broad class probe also addresses unrelated vendor-specific or still-image devices.

**Likely:** vendored libusb compiles on desktop targets but does not provide Windows driver binding or Linux udev access. **Confirmed:** CI never builds the Android module, and tests omit discovery, cancellation, Activity lifecycle, Android JSON handling, and frontend recovery.

<summary>Details</summary>

## HIGH — URL launch conflicts with Activity-owned transport

**Confidence: likely.** `MainActivity.openUrl` posts `startActivity(Intent.ACTION_VIEW, uri)` and waits for that task at `android-companion/app/src/main/java/com/scrcpyguiplus/companion/MainActivity.kt:339-369`. A normal full-screen browser launch moves the companion Activity to `onStop`, which immediately calls `disconnectConnection()` at `MainActivity.kt:89-94`; `AccessoryConnection.stop` closes the descriptor used by the request worker. Depending on lifecycle scheduling, the success response is written just before shutdown or loses the descriptor first. Either outcome makes `open_url` terminal while the desktop retains a connected device.

The documented foreground-only MVP trade-off conflicts with this method's own behavior. Move connection ownership outside the Activity lifecycle, or define URL launch as terminal, acknowledge it before launching, and clear desktop state immediately.

## HIGH — Per-transfer timeouts leave operations uncancellable

**Confidence: confirmed.** `USB_TIMEOUT` is reapplied inside every partial `read_bulk` and `write_bulk` loop (`src-tauri/src/companion.rs:27`, `143-158`, `188-204`). `scan_for_companion` performs ten rescan attempts (`companion.rs:386-414`), each of which can wait five seconds for a hello; repeated hello timeouts alone can consume roughly 53.5 seconds. Candidate control requests add more waits, and periodic partial progress can extend a frame indefinitely because no total deadline is measured.

```text
CompanionPanel
    -> Tauri command
       -> Mutex<Option<CompanionConnection>> held for the operation
          -> libusb I/O (5 s per transfer, not per operation)
             -> Android worker -> optional main-thread action
```

**Confidence: confirmed.** `companion_scan` and `companion_request` hold that mutex through discovery and I/O (`companion.rs:518-560`), while `companion_disconnect` waits for it (`companion.rs:564-571`). The panel disables disconnect during a request (`src/components/companion/CompanionPanel.tsx:136-140`) and offers none during an initial scan. Add a total deadline, cancellation that can close the active handle, and lock ownership that does not queue cancellation behind blocked I/O. Android's `openUrl` wait is also exactly five seconds (`MainActivity.kt:362`), leaving no margin before the host's response read expires.

## MEDIUM — Backend liveness and React “Connected” state diverge

**Confidence: confirmed.** `companion_scan` returns a cached `CompanionDevice` without a ping or descriptor check (`src-tauri/src/companion.rs:518-537`). `connect_and_request` clears the backend connection after write/read failure (`companion.rs:482-514`), but `useCompanion.request` only records the error (`src/hooks/useCompanion.ts:40-59`), and `CompanionPanel` derives its badge solely from `devices[0]` (`src/components/companion/CompanionPanel.tsx:43`, `118-133`). Unplug or transport failure therefore leaves actions enabled against a discarded session.

Return a typed disconnected result, clear the device on transport failure, emit removal events where possible, and liveness-check cached handles during scan.

## MEDIUM — Privileged methods have no peer authentication

**Confidence: confirmed.** The host accepts any protocol-1 hello with a non-empty self-reported package (`src-tauri/src/companion.rs:301-364`). Android accepts any host presenting the public AOA strings after accessory permission, then exposes `clipboard_get`, `clipboard_set`, and `open_url` through `MainActivity.handleFrame` (`MainActivity.kt:283-318`). Physical USB access and the permission dialog mitigate exposure, but remain the entire authorization model for clipboard disclosure and URL launch.

**Confidence: confirmed.** Rust caps clipboard text at 256 KiB and URLs at 4096 bytes (`companion.rs:417-448`), while `MainActivity.clipboardSet` and `openUrl` only check types, blankness, and scheme (`MainActivity.kt:322-349`). Another accessory host can bypass the desktop limits. Add explicit in-app session consent plus pairing or a per-installation challenge, enforce bounds on Android, and validate expected package/capabilities for accidental mismatch; self-reported package checks alone are not authentication.

## MEDIUM — Discovery commits before identifying the companion

**Confidence: confirmed.** `scan_for_companion` stops at the first device for which `switch_to_accessory` succeeds (`src-tauri/src/companion.rs:386-399`), before app identity is available. With two phones attached, a first phone without the companion can consume every rescan while a later phone with the app is never considered. Continue across candidates under one overall deadline or let the user select a physical device and retain bus/port identity through re-enumeration.

**Confidence: likely.** `is_android_candidate` accepts class `0x00`, every vendor-specific interface, and still-image devices, then sends the AOA vendor request (`companion.rs:218-240`, `263-299`). Non-Android cameras and proprietary hardware can match that filter; most will stall, but they still receive a control probe. Narrow descriptor matching and identify the target device before attempting the switch.

## MEDIUM — Protocol failures neither reset nor diagnose the session

**Confidence: confirmed.** `connect_and_request` clears the connection for USB write/read errors but returns `decode_response` failures without clearing it (`src-tauri/src/companion.rs:482-514`). Invalid JSON, wrong frame type, missing ID, or ID mismatch leaves a stream active after its strict transaction contract was violated. Preserve the session only for a structurally valid `ok: false` response; malformed or mismatched frames should force a new hello.

**Confidence: confirmed.** `find_open_accessory` discards every `open_and_identify` error (`companion.rs:373-384`). Driver denial, endpoint failure, hello timeout, malformed hello, and protocol mismatch all become “not found.” Preserve the most relevant error for recognized AOA VID/PIDs and expose typed failure reasons to the panel.

## MEDIUM — Vendored libusb does not complete Windows/Linux access

**Confidence: likely.** `src-tauri/Cargo.toml:38` vendors `rusb`/libusb at build time, but does not bind Android/AOA interfaces to WinUSB or install Linux udev permissions. Releases target Windows, Linux, and macOS (`.github/workflows/release.yml:19-28`) without driver setup, udev rules, or companion-specific diagnostics; access must also survive re-enumeration to Google's AOA VID/PIDs.

Document or bundle a Windows driver strategy that does not unexpectedly replace ADB/MTP bindings, ship scoped Linux udev rules, and preserve permission/driver errors instead of returning “No Android companion found.”

## MEDIUM — Core behavior is outside automated coverage

**Confidence: confirmed.** Rust tests (`src-tauri/src/companion.rs:574-615`) cover validation and response decoding but cannot exercise enumeration, retry timing, invalidation, cancellation, or multi-device selection. Android has only `FrameCodecTest`; `ProtocolJson`, permission delivery, Activity lifecycle, request bounds, and URL disconnect are untested. No hook/panel tests cover recovery, and `.github/workflows/pull_request.yml` never runs an Android build or `gradlew test`.

Local TypeScript lint, the six Sidebar tests, four Rust companion tests, and seven Android framing tests pass. Add a fakeable host transport, JVM protocol/bounds tests, lifecycle or instrumentation coverage, frontend recovery tests, Android CI, and a physical AOA smoke test; the module itself records that hardware integration is unverified (`android-companion/README.md:75-81`).

## LOW — The install path points away from this companion

**Confidence: confirmed.** The AOA URI is `https://github.com/Genymobile/scrcpy` (`src-tauri/src/companion.rs:287-292`), while the sidebar asks users to install this companion. Releases publish only desktop artifacts, and `android-companion/README.md:20-29` requires building and ADB-installing a debug APK. Point the URI at companion installation instructions or a signed APK and publish that artifact before presenting the feature as end-user installable.
