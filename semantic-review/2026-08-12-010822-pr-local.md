# QR/LAN Android companion control and JPEG screen streaming

This change adds a standalone Android companion, Rust AOA/LAN control transport, and a view-only QR/LAN screen stream. The desktop uses bounded length-prefixed JSON for control and a second authenticated TCP socket for JPEG frames, while React receives frames through a Tauri binary `Channel` and revokes replaced blob URLs. Framing and request validation are solid, but the MediaProjection runtime contract and several screen teardown paths are not safe yet. **Watch for:** **confirmed** target-SDK-35 MediaProjection lacks the required foreground-service contract; **likely** the permission Activity triggers the companion's `onStop` teardown; **confirmed** screen stop can block behind an unbounded writer; **confirmed** Rust and React screen generations diverge after LAN pairing; **confirmed** the screen listener has no pre-connect expiry.

**Verdict**: NEEDS_CHANGES

## High-level view

The desktop keeps companion state separate from ADB/scrcpy and serializes control requests. It avoids the ADB descriptor after AOA re-enumeration and now has total operation deadlines, but switching a phone into AOA mode can still disrupt an active USB workflow.

The two-socket design gives control requests and JPEG frames independent lifecycles, with bounded framing and token/generation validation. The screen listener has no timeout before Android connects, and Android's writer cannot reliably be interrupted during backpressure.

Android owns both sessions from the foreground Activity. **Confirmed** target-SDK-35 MediaProjection needs a foreground-service contract, and **likely** the system consent Activity can trigger the `onStop` policy that clears the pending request. React has stale-frame/blob cleanup, but **confirmed** generation drift drops screen status events and screen-request failures can leave a stale Connected badge.

The LAN token is one-time authentication, not encryption: **confirmed** control, clipboard, URL, screen hello, and JPEG bytes are plaintext. Existing unit suites cover pure protocol logic, not the screen channel, lifecycle, or ImageReader path.

<summary>Issues (11)</summary>

1. **HIGH — MediaProjection foreground-service contract (confirmed)** — The target-35 Android app has no `FOREGROUND_SERVICE_MEDIA_PROJECTION` declaration or mediaProjection foreground service, so screen capture can fail at runtime on Android 14+. Add the required service/notification contract or change the supported API/target strategy.
2. **HIGH — Permission dialog tears down the Activity-owned session (likely)** — `onStop()` clears the pending screen offer and closes the control connection while the system capture-consent Activity may be in front. Keep the request alive through the result or move capture/session ownership out of the Activity.
3. **HIGH — Screen stop cannot interrupt a blocked writer (confirmed)** — The writer holds `outputLock` during an unbounded socket write, while `stopInternal` waits for that lock before closing the socket. Close/cancel the socket first and avoid blocking flush/close work on the UI lifecycle thread.
4. **HIGH — Stop/connect race leaks a stale capture (confirmed)** — A stop during `Socket.connect()` closes no socket because it has not been assigned yet; the worker then creates a display and sends a hello after `running` is already false. Coordinate worker startup and check the running epoch before setup and hello.
5. **HIGH — Screen listener has no pre-connect expiry (confirmed)** — Permission denial, a background Activity, or a missing MediaProjection manager leaves the Rust listener and ephemeral port polling forever because only post-connect hello/frame reads have deadlines. Add a setup deadline and propagate Android startup failure/cancellation.
6. **MEDIUM — Rust/React screen generations drift (confirmed)** — LAN pairing invalidates Rust's screen epoch before the frontend initializes its local generation, so normal first-start statuses use different numbers and are discarded. Return one authoritative generation or remove the duplicate frontend counter.
7. **MEDIUM — One invalid screen peer terminates the listener (confirmed)** — A private-LAN client with a wrong token, malformed hello, or bad JPEG reaches the error return that ends the listener; the rejected-client budget only applies to disallowed addresses. Continue accepting bounded retries until expiry.
8. **MEDIUM — Screen request failures leave stale connected UI (confirmed)** — `startScreen` and `stopScreen` do not apply the `disconnected` envelope handling used by ordinary requests. When Rust drops a lost control session, React can retain the device badge and enabled controls.
9. **MEDIUM — LAN control and screen data are plaintext (confirmed)** — The one-time token does not provide confidentiality or protect against an on-path LAN client that observes it. Add pinned TLS before treating LAN as usable on an untrusted network, or keep the trusted-network limitation explicit in product gating.
10. **MEDIUM — AOA discovery is disruptive and incomplete (likely)** — USB scanning sends `AOA_START` to every allowlisted vendor candidate without selecting an ADB device, which can re-enumerate and disrupt an active scrcpy/control session, while valid OEMs outside the fixed VID list are skipped. Require an explicit target/warning and preserve an identifiable device selection.
11. **LOW — The real screen path is outside automated coverage (confirmed)** — Tests do not cover the Tauri raw channel, Rust screen sockets/retries, Android permission/lifecycle/FGS behavior, writer cancellation, or ImageReader stride buffers. Add fakes/instrumentation and an API-34/35 hardware smoke flow before relying on the passing unit suites.

## AOA discovery and existing USB control sessions

**Confidence: likely for the runtime disruption; confirmed for the code path.** `companion_scan` probes every device matching the fixed `ANDROID_VENDOR_IDS` list and `switch_to_accessory` sends the AOA handshake before companion identity is known (`src-tauri/src/companion.rs:867-948`, `1137-1165`). Switching USB functions can interrupt an existing ADB/scrcpy connection; the separate `CompanionState` mutex cannot prevent that physical re-enumeration. The allowlist also creates false negatives for Android OEMs not listed.

`open_usb` prefers the `ff/ff/00` AOA interface and excludes the `ff/42/01` ADB interface (`companion.rs:481-548`), so the remaining compatibility issue is discovery policy, not control framing. Limit probing to an identified/user-selected device, warn before switching USB functions, and retain identity across re-enumeration.

## MediaProjection permission and Activity ownership

**Confidence: confirmed for the API contract.** `android-companion/app/build.gradle.kts:17` targets SDK 35, but `AndroidManifest.xml` declares only `INTERNET` and no `FOREGROUND_SERVICE`/`FOREGROUND_SERVICE_MEDIA_PROJECTION`; there is no foreground service. `MainActivity.onActivityResult` calls `getMediaProjection`, and `ScreenCaptureSession` creates the virtual display from that Activity-owned object (`MainActivity.kt:611-682`, `ScreenCaptureSession.kt:119-157`). On Android 14+ a target-34+ MediaProjection app must use the mediaProjection foreground-service type and its permissions/notification. The project can build and pass JVM tests while capture fails with a runtime security exception. Add a real mediaProjection foreground service and move capture ownership there, or deliberately constrain target/API support.

**Confidence: likely for the consent lifecycle failure.** `requestScreenCapture` stores `pendingScreenOffer` and launches the system consent Activity, but `MainActivity.onStop` calls `stopScreenCapture`—which clears that offer—and `disconnectConnection` (`MainActivity.kt:97-112`, `584-610`). The full-screen consent Activity can make the source Activity stopped; `onActivityResult` then sees no offer and drops a valid grant. Keep the session alive through consent and use explicit pending-consent lifecycle rather than unconditional connection teardown in `onStop`.

## ScreenCaptureSession teardown and the second socket

**Confidence: confirmed.** The writer holds `outputLock` around `FrameCodec.writeScreenFrame`, whose socket write/flush has no write deadline (`ScreenCaptureSession.kt:196-218`, `FrameCodec.kt:99-137`). `stopInternal` waits for that lock and flushes before closing `socket` (`ScreenCaptureSession.kt:265-296`). Under backpressure, the writer can remain blocked while the UI lifecycle thread waits; closing the socket—the operation that would unblock it—cannot happen until after that wait. Close/cancel the socket before acquiring the lock, avoid a stop-time flush, and make writer cancellation explicit.

**Confidence: confirmed.** `connectAndCapture` assigns `socket` only after `connect()` returns and then unconditionally calls `setupCapture` and writes `screen_hello` (`ScreenCaptureSession.kt:84-116`). A stop during the five-second connect window sees `socket == null`, sets `running` false, shuts down the writer, and returns; the worker can then create a VirtualDisplay and send on a stale socket. Check the session epoch after connect and before setup/hello, close the local socket on the stopped path, and serialize worker start/stop.

Both ends agree on four-byte big-endian lengths, bounded hello/frame allocations, token/generation validation, and JPEG start/end checks (`src-tauri/src/companion.rs:1290-1360`, `1536-1651`; `FrameCodec.kt:20-105`). `imageToBitmap` accounts for row padding by creating a padded bitmap and cropping it (`ScreenCaptureSession.kt:226-263`); no concrete padding arithmetic defect was found, but there is no device test for nontrivial plane buffers, crop rectangles, or rotation.

## Rust screen listener admission and cancellation

**Confidence: confirmed.** `run_screen_stream_listener` has no overall deadline around its nonblocking `accept` loop (`src-tauri/src/companion.rs:1536-1651`). `companion_screen_start` returns after Android acknowledges the control request, before permission or the second socket completes (`companion.rs:1951-2074`). If Android denies permission, is backgrounded, lacks a usable manager, or never reaches the socket, the listener polls indefinitely; `SCREEN_HELLO_TIMEOUT` starts only after a client connects. Add a setup deadline, cancel it when the control session disappears, and report Android startup failure. Android also has no independent first-frame watchdog and only notices a remotely closed screen socket on a later write, so the ends need coordinated timeout/stop behavior.

**Confidence: confirmed.** Once a private-LAN peer is accepted, any hello/JPEG error emits `error` and returns. `SCREEN_MAX_REJECTED_CLIENTS` applies only to disallowed addresses (`companion.rs:1555-1560`, `1621-1651`). A stale attempt, wrong-token client, or port scanner can consume the one screen attempt and prevent reconnect. Treat protocol/authentication failures as rejected clients and continue until a bounded rejection count or setup expiry.

## Screen generation, Tauri channel, and UI recovery

**Confidence: confirmed.** Rust and React maintain independent screen counters that are already offset in the normal LAN flow:

```text
Rust:   screen_epoch 1 --LAN start invalidates--> 2 --screen start returns--> 3
React:  local generation 0 --connected reset--> 1 --screen start uses--> 2
```

`companion_lan_start` invalidates the backend counter before pairing (`companion.rs:1881-1884`), while `useCompanion` increments its local counter on connected and again at `startScreen` (`useCompanion.ts:54-60`, `299-325`). The hook therefore discards Rust's status events at `useCompanion.ts:117-139`. Frames can still appear because the Channel callback closes over the frontend number, but a denied/no-frame start remains stuck in `isScreenStarting`, and stop status remains “Stopping”. A failed backend start can increment Rust's epoch without telling React. Return the backend generation in the start response/status and use one authoritative token.

**Confidence: confirmed.** Ordinary `useCompanion.request` clears `devices` when Rust returns `disconnected`, but `startScreen` and `stopScreen` invoke specialized commands directly and only inspect `success` (`useCompanion.ts:236-284`, `327-376`). If a screen control request loses the LAN socket, Rust can drop the session while React retains `devices[0]`, the Connected badge, and enabled controls. Share the ordinary response/session recovery path and emit a companion disconnected event when the backend loses control.

The Channel callback ignores old generations, each frame revokes the previous object URL, and hook cleanup revokes the last URL (`useCompanion.ts:48-60`, `312-325`, `398-405`). The actual raw delivery and a hook-unmount/late-channel scenario remain untested.

## LAN trust boundary

**Confidence: confirmed.** The desktop authenticates the first control hello with a random token, but sends that token and subsequent control data in plaintext. The second screen socket repeats the pattern with another plaintext token and JPEG stream (`companion.rs:1225-1244`, `1951-2040`; `ScreenCaptureSession.kt:84-116`). A passive/on-path LAN client can observe tokens and clipboard contents; an active client can race pairing or interfere with screen/control traffic. The README documents this trusted-network MVP trade-off, but TLS with a pinned certificate or product-level network restriction is required before treating QR/LAN as a general secure transport.

## Test boundary and verified behavior

**Confidence: confirmed for missing coverage.** `npm run lint`, 216 frontend tests, `cargo check`/135 Rust tests, `./gradlew test assembleDebug`, and `./gradlew lint` pass. Android tests cover pure framing, JSON, processor recovery, and input byte limits; Rust tests cover pure validation/decode paths. None exercise `Channel<InvokeResponseBody>::Raw`, the Rust second-socket listener, rejected-client retry, permission denial, Activity `onStop`/`onActivityResult`, foreground-service startup, writer cancellation, or a real `ImageReader` plane. `useCompanion.test.ts` does not mock or call screen start/stop service functions, and panel tests contain no screen-capability case. Add deterministic socket fakes, hook/channel tests, API-34/35 lifecycle/instrumentation tests, and a physical LAN/MediaProjection smoke test covering padded images, rotation, denial, stop, reconnect, and desktop close.
