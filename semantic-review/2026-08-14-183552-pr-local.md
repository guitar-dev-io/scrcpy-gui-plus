# Auto Screen Capture lifecycle and screenshot-history integration

This change adds an asynchronous Auto Screen Capture workflow that samples bounded ADB PNG frames, scrolls through an existing scrcpy control session when available, aligns/stitches the new content, and exports a typed result. The React hook subscribes to backend lifecycle events and exposes pause, resume, stop, and cancel controls; the application records completed results in the existing screenshot history. The backend’s terminal arbitration and region-aware capture logic are covered by focused tests, but the frontend still treats event delivery and IPC response ordering as if they were serialized. Watch for: **confirmed** a terminal event can be overwritten by a later stale start/stop/cancel response, **likely** a missed terminal event leaves the UI active and omits the history entry, and **confirmed** the history’s segment count includes end-confirmation frames.

**Verdict**: NEEDS_CHANGES

## High-level view

The Rust side owns one capture job per device, emits typed lifecycle payloads, and seals terminal metadata under the session mutex. The frontend applies event and IPC snapshots through separate paths, so backend publication safety does not make the displayed session monotonic.

`useAutoCapture` binds events by session ID once it has one, falls back to the current device before the start response arrives, and has no backend reconciliation path. Active-device changes can leave the panel labeled for one device while controls and events remain bound to another.

The result is added to screenshot history with a session-based duplicate guard, but the history’s `segmentCount` is populated from a probe-inclusive capture count rather than the number of stitched regions. The visible gallery can therefore report more segments than the exported image contains.

The focused tests cover command forwarding, a normal event stream, duplicate terminal events, panel controls, pure capture algorithms, and atomic control primitives; they do not exercise the cross-layer orderings or history bridge that determine these risks.

<details>
<summary>Issues (6)</summary>

1. **Non-monotonic terminal state** — A terminal event can be overwritten by a later `start`/`stop`/`cancel` IPC snapshot, leaving the UI active after output publication. Merge all snapshots through a terminal-aware, timestamp-ordered path and notify completion from that path.
2. **No lifecycle reconciliation** — If a lifecycle event is missed, the hook never fetches the retained backend session, so it can remain active indefinitely and fail to add the result to history. Reconcile after start/control calls and on hook initialization or event-listener recovery.
3. **Capture device ownership drift** — Changing the active device during capture relabels the panel/config while commands still target the old session; the pre-ID device fallback can also claim an unrelated same-device event. Lock the device or make the bound session device authoritative and correlate the initial event to the start request.
4. **Incorrect history segment count** — `ScreenshotHistoryEntry.segmentCount` receives the session’s accepted-frame count, including no-new-content confirmations, rather than stitched-region count. Export a separate segment count or stop using the probe-inclusive value for the gallery badge.
5. **Frontend type/runtime MVP mismatch** — Frontend types permit UP/LEFT/RIGHT and JPEG, while the backend intentionally rejects them with typed errors. Narrow or explicitly document the public config contract so callers are not offered guaranteed failures.
6. **Missing lifecycle integration coverage** — The tests do not cover event/response reordering, dropped-event recovery, device switching, or `recordAutoCapture`. Add deterministic integration tests that assert terminal state and exactly one history entry.

## Terminal events are not monotonic in the React session state

**Confidence: confirmed.** `start_auto_capture` snapshots the session in `STARTING`, emits `auto-capture-started`, spawns the worker, and returns that same snapshot (`src-tauri/src/auto_capture/controller.rs:473-518`). The worker can finish before the `invoke` promise callback runs, especially for a one-frame or immediately failing job. The hook’s event handler publishes the terminal session and calls `onCompleted`, but `start` then unconditionally assigns the older `started` snapshot to `sessionRef` and React state (`src/hooks/useAutoCapture.ts:234-240`). That can leave a completed job displayed as `STARTING`/active after its result has already been written to history.

The same ordering problem exists for control commands. `stop_auto_capture` and `cancel_auto_capture` atomically change the control word but return a snapshot of the current session; the worker can publish `STOPPED` or `CANCELLED` before that response is delivered. `command` then replaces a terminal state with the response snapshot without merging or checking timestamps/status (`src-tauri/src/auto_capture/controller.rs:546-576`, `src/hooks/useAutoCapture.ts:250-262`). A stale pause/resume response can produce the same regression when a terminal event wins the race.

```text
terminal event -> session = COMPLETED, onCompleted(result)
                         ^
                         | later IPC callback
start/stop response -> session = STARTING or CAPTURING
```

Make session updates monotonic by session ID and event/snapshot timestamp, or centralize all event and command responses through one merge function that refuses to replace a terminal snapshot with a non-terminal one. Terminal-result notification should be part of that same path rather than being exclusive to event callbacks.

## Missed lifecycle events have no session reconciliation path

**Confidence: likely.** The hook starts an asynchronous `Promise.all` listener registration and does not wait for it before allowing `start`; the backend’s start command always returns the pre-worker `STARTING` snapshot. If listener setup is late, a window reloads, or an event is otherwise dropped, there is no later state fetch: `getAutoCaptureSession` exists in `autoCaptureService.ts` but is never imported or called by `useAutoCapture` (`src/services/autoCaptureService.ts:29-33`, `src/hooks/useAutoCapture.ts:128-184`).

A missed terminal event therefore leaves the hook with a non-terminal session and `isActive=true` even though the backend has removed the job from `active_by_device`. Because `onCompleted` is also invoked only from the event handler, the final PNG is absent from screenshot history in this case. A terminal snapshot returned by a stop/cancel command does not repair that omission because `command` only updates React state.

Fetch the session after start and after control commands, or poll/reconcile until a terminal status; route a terminal response through the same completion callback with the existing session/result ID dedupe.

## Active-device changes do not follow the bound capture session

**Confidence: confirmed.** Once `sessionIdRef` is set, the event filter accepts only that ID and no longer checks `activeDeviceRef` (`src/hooks/useAutoCapture.ts:131-145`). There is no effect that locks or resets the hook when `activeDevice` changes. The panel, however, continues to receive the new `activeDevice`, and its config effect rewrites `config.deviceId` and output settings while the pause/stop/cancel callbacks still target the old `sessionIdRef` (`src/components/auto-capture/AutoScreenCapturePanel.tsx:91-99`, `src/hooks/useAutoCapture.ts:250-278`). Switching from device A to B during a capture can therefore show B in the panel while commands and lifecycle events still belong to A.

Before a session ID is known, the fallback accepts any matching-device event and claims its ID. That is **likely** to attach a freshly mounted hook to an unrelated same-device job in a reload or multi-window scenario because there is no start-request correlation; the backend’s per-device busy guard does not identify which frontend initiated the job.

Lock device selection for an active session, or make the session’s device the authoritative label/command context and explicitly reconcile on a device switch. Do not adopt an event solely by device when a start request has not been correlated to its returned session.

## Screenshot history labels probe-inclusive counts as stitched segments

**Confidence: confirmed.** `accept_frame` increments `AutoCaptureSession.capture_count` for each settled frame before overlap classification (`src-tauri/src/auto_capture/controller.rs:1609-1621`). End confirmation frames can be accepted but not appended to `LongScreenshotBuilder`; `finalize_capture` nevertheless passes the session count into `AutoCaptureResult.capture_count` (`controller.rs:1312-1338`). `useScreenshot.recordAutoCapture` copies that value into `ScreenshotHistoryEntry.segmentCount` (`src/hooks/useScreenshot.ts:232-245`), which the gallery displays in the scroll badge.

A capture with four stitched regions followed by two no-new-content confirmations can thus report six “segments” even though only four regions were exported. Keep separate `captureCount` and stitched-segment count fields, or derive the history badge from the builder’s accepted segment count.

## Frontend configuration types expose rejected MVP options

**Confidence: confirmed.** The shared `ScrollDirection` type includes `UP`, `LEFT`, and `RIGHT`, and `AutoCaptureOutputFormat` includes `JPEG` (`src/types/autoCapture.ts:14-16`), while Rust validation rejects every direction except `DOWN` and every format except `PNG` (`src-tauri/src/auto_capture/model.rs:342-357`). The panel currently exposes only DOWN and defaults to PNG, so the visible UI is consistent with the MVP; the service/type surface still lets callers construct configurations that are statically valid but guaranteed to fail with `UNSUPPORTED_DIRECTION` or `UNSUPPORTED_OUTPUT_FORMAT`.

Either narrow the frontend contract to the implemented MVP or explicitly model the unsupported values as reserved/future options and document the validation boundary.

## Lifecycle and history integration are not covered by the current tests

**Confidence: confirmed.** The frontend tests cover service IPC arguments, listener teardown, a normal event sequence, duplicate terminal events, and panel actions (`src/services/autoCaptureService.test.ts`, `src/hooks/useAutoCapture.test.ts`, `src/components/auto-capture/AutoScreenCapturePanel.test.tsx`). They do not cover event-before-start-response, terminal-event-before-command-response, missed events/reconciliation, active-device switching, or `useScreenshot.recordAutoCapture`; there is no focused `useScreenshot` history test. Rust tests cover the controller’s atomic primitives and pure capture algorithms, but not the Tauri command/event delivery or the existing embedded control socket in an auto-capture run.

Add integration-level tests for those orderings and assert both final session state and exactly one history entry. Keep the ignored real-device scroll smoke test separate from deterministic lifecycle tests. Current targeted validation passes: the three frontend feature test files (8 tests), `cargo test auto_capture --lib` (31 tests), `npm run lint`, `cargo fmt -- --check`, and `cargo check --lib`.
